# Karsa Data Ingestion API

> Create individual and business customers, guarantee beneficial owners are individual Customer records, and submit verification, account, document, transaction, and outcome data to Karsa.

> ## Agent Instructions
> Document only operations in the linked OpenAPI contract: the source-data ingestion operations and the source-scoped outbound webhook management operations.
> Treat the generated OpenAPI document as authoritative for request fields. Never invent compatibility fields, alternate endpoints, or additional source models.
> Preserve explicit nulls, decimal strings, timestamps, source identifiers, immutable version identifiers, and document-version links exactly as defined.

- [Upload an account](https://docs.useasterisk.com/api-reference/accounts/upload-an-account.md): Uploads one bank-account, virtual-account, or wallet snapshot, its optional customer relationship, structured routing details, related accounts, and document links.
- [Update an account](https://docs.useasterisk.com/api-reference/accounts/update-an-account.md): Updates supplied mutable fields and appends a complete immutable account snapshot. Stable Karsa and source identifiers, accountKind, and accountType are not replaceable.
- [Submit a document](https://docs.useasterisk.com/api-reference/documents/submit-a-document.md): Submit exactly one of contentBase64 or sourceUrl. Bytes are stored immediately; HTTP(S) URLs are retained verbatim as PENDING_DOWNLOAD references without fetching or signing. URL acceptance does not establish file availability. contentType describes the declared file type.
- [Upload a transaction](https://docs.useasterisk.com/api-reference/transactions/upload-a-transaction.md): Writes known subjects and partial sent/received money legs without inventing missing counterparties.
- [Update a transaction](https://docs.useasterisk.com/api-reference/transactions/update-a-transaction.md): Updates supplied mutable fields and appends a complete immutable transaction snapshot. Stable Karsa and source identifiers and transactionType are not replaceable.
- [Record a source completeness checkpoint](https://docs.useasterisk.com/api-reference/sources/record-a-source-completeness-checkpoint.md): Attests that the authenticated source has delivered every record for the named dataset from completeFrom (or source inception when null) through completeThrough. Checkpoints are append-only, cannot regress, and are resolved at a routine's frozen evidence cutoff.
- [Upload an outcome](https://docs.useasterisk.com/api-reference/outcomes/upload-an-outcome.md): Records one source outcome against exactly one subject.
- [Upload a provider screening observation](https://docs.useasterisk.com/api-reference/screening/upload-a-provider-screening-observation.md): Records an immutable, provider-neutral AiPrise, SEON, Chainalysis, or other verification, fraud, AML, transaction-monitoring, or blockchain-screening observation. This preserves source evidence and does not itself create a Karsa finding or queue decision.
- [Upload a native SEON Fraud API response](https://docs.useasterisk.com/api-reference/screening/upload-a-native-seon-fraud-api-response.md): Accepts the native SEON response plus a Karsa subject binding. Karsa validates and normalizes the provider result while retaining the bounded native response for audit.
- [Upload a native AiPrise verification response](https://docs.useasterisk.com/api-reference/screening/upload-a-native-aiprise-verification-response.md): Accepts the native AiPrise verification response plus a Karsa subject binding and KYC/KYB scope. Karsa owns result normalization; related-party data remains evidence until separately mapped to canonical subjects.
- [Upload a native Chainalysis alert response](https://docs.useasterisk.com/api-reference/screening/upload-a-native-chainalysis-alert-response.md): Accepts the contracted Chainalysis product's alert envelope plus explicit product, API version, provider record identity, and Karsa subject binding. Unknown response states fail closed as UNKNOWN.
- [Upload a screening disposition](https://docs.useasterisk.com/api-reference/screening/upload-a-screening-disposition.md): Records an immutable reviewer or source-system disposition tied to an existing screening observation from the same authenticated source. It remains distinct from Karsa's recommendation and any later Finding disposition.
- [Upload a monitoring control version](https://docs.useasterisk.com/api-reference/controls/upload-a-monitoring-control-version.md): Records one immutable version from the authenticated source's authoritative control catalog. Scope, depth, and configuration fingerprints allow overlap and change analysis without treating vendor alerts as the catalog.
- [Upload a monitoring control execution](https://docs.useasterisk.com/api-reference/controls/upload-a-monitoring-control-execution.md): Records one immutable scheduled or completed control execution tied to a monitoring-control version from the same authenticated source. Result, alert, and disposition references remain source identifiers and do not themselves create a Karsa decision.
- [Upload a historical RFI lifecycle event](https://docs.useasterisk.com/api-reference/requests/upload-a-historical-rfi-lifecycle-event.md): Records one immutable request, response, expiry, closure, or cancellation event for a source-owned RFI. Events retain the source request identity and customer binding needed to measure repeat requests and expiry without exposing response contents.
- [List webhook endpoints](https://docs.useasterisk.com/api-reference/webhooks/list-webhook-endpoints.md): Lists only destinations owned by the authenticated ingestion source.
- [Create a webhook endpoint](https://docs.useasterisk.com/api-reference/webhooks/create-a-webhook-endpoint.md): Accepts one customer-generated Ed25519 key pair. Karsa validates the pair, encrypts the private key, and never returns it. The endpoint remains inactive until verification succeeds.
- [Update a webhook endpoint](https://docs.useasterisk.com/api-reference/webhooks/update-a-webhook-endpoint.md): Changing an active destination URL returns the endpoint to pending verification. A disabled endpoint stays disabled and must be enabled before verifying its new URL.
- [Delete a webhook endpoint](https://docs.useasterisk.com/api-reference/webhooks/delete-a-webhook-endpoint.md): Stops new deliveries and retains a read-only endpoint archive with delivery history for the retention period.
- [Verify a webhook endpoint](https://docs.useasterisk.com/api-reference/webhooks/verify-a-webhook-endpoint.md): Sends a signed challenge. The receiver must return a 2xx JSON response with the exact challenge.
- [Enable a webhook endpoint](https://docs.useasterisk.com/api-reference/webhooks/enable-a-webhook-endpoint.md): Resumes new deliveries for this endpoint.
- [Disable a webhook endpoint](https://docs.useasterisk.com/api-reference/webhooks/disable-a-webhook-endpoint.md): Pauses new deliveries for this endpoint.
- [Rotate a webhook signing key](https://docs.useasterisk.com/api-reference/webhooks/rotate-a-webhook-signing-key.md): Validates and encrypts a new customer-generated Ed25519 key pair. The prior public key remains in an overlap window at least as long as delivery retries.
- [Send a test webhook](https://docs.useasterisk.com/api-reference/webhooks/send-a-test-webhook.md): Queues a durable webhook.test event through the normal delivery relay.
- [List webhook delivery history](https://docs.useasterisk.com/api-reference/webhooks/list-webhook-delivery-history.md): Returns bounded delivery and attempt history for the source-owned endpoint, including a deleted endpoint retained as a read-only archive.
- [Retry a failed webhook delivery](https://docs.useasterisk.com/api-reference/webhooks/retry-a-failed-webhook-delivery.md): Requeues a dead-lettered delivery without changing its event, body, timestamp, key version, or signature.
